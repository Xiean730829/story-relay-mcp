# 灵矽游戏大厅设计总图

灵矽以无屏幕语音盒子为入口。每个孩子带着自己的 Buddy 进大厅。一楼负责把人、场次和可复用原声接起来，二楼由各个房间定义玩法。故事接龙是首个房间，用来验证好友同局和离线好友原声复用。

**通信基线**按未来一年的小规模好友语音房来定，采用半双工短回合。场次先给一个玩家发言权。语音侧收完一句，区分私人控制和游戏动作，经房间接收后，才把原声播到指定盒子。在线同局和历史回放共用播放、交棒和取消能力。

## 故事接龙房间

故事接龙的最小单位是玩家说完的一段原声。房间把段落按故事位置串起来。开局时可以由孩子、Buddy 或一段可独立使用的历史开头起笔。Buddy 参与时，由房间决定它能否接句。孩子可以继续编、结束这一局，或选择留下一句供之后使用。

| 玩法 | 房间推进方式 |
| --- | --- |
| 和 Buddy 玩 | 孩子与自己的 Buddy 轮流接句。由房间安排谁开头、什么时候收尾。 |
| 好友同局 | 两位好友各自入座。当前玩家说完后，另一位听到原声，再获得接话机会。 |
| 好友错时玩 | 可以用好友留下的合适开头开启新局，也可以恢复已有故事并听取对应位置的续句。播放前由 Buddy 说明声音的来源。 |

房间保存故事进度和段落关系，平台保存通用场次状态、音频引用和复用权限。玩家退出时，房间按当前进度决定结束或留下待续入口。每一段声音能否入池、能在新故事里开头还是只能用于当前故事的位置，由房间声明。

## 房间运行和语音控制

场次服务拥有成员、发言权和事件顺序，房间拥有玩法状态。房间可以提出「给 B 播这段原声，播完后请 B 接一句」。语音侧执行后回传播放状态，场次根据当前回合把结果交给房间。Buddy 只接收当前孩子可见的局面和可用动作，可以解释、提醒和帮助孩子表达选择。规则判定、发言授权和录音发布分别由房间、场次及复用池执行。

**普通发言遵守发言权，明确退出直接走私人控制。** 别人正在说时，插话和抢答留在本机。轮到自己时，采集的一句先在该玩家的语音会话里识别用途，再交给房间。明确说「不玩了」或「换个游戏」时，先结束本机游戏播放和收音，释放发言权并通知场次。孩子说「停一下」时，先停本机播放，保留场次，再让 Buddy 确认下一步。播放中触发私人控制的方式需要按机型验证，现有设备中断和唤醒后回到 Buddy 是接入起点。

## 通信与存储设计

### 一次回合怎么交接

~~~text
房间指定下一位发言者
  → 场次授予发言权，语音侧提示并开麦
  → 玩家说完一句，语音侧区分私人控制和游戏动作
  → 场次校验身份及回合，房间接收动作
  → 指定盒子播放原声
  → 下一位的盒子播完，或触发房间定义的超时处理
  → 场次释放旧回合，按房间结果开启后续动作
~~~

历史音频从「指定盒子播放原声」进入同一条交接路径。在线发言携带来自本次采集的音频引用，历史发言携带经过授权的存储引用。来源类别随动作一起传递，Buddy 可以介绍素材的来历。

### 跨仓协议草案

- **设备连接**沿用灵矽现有 WebSocket。原声音频由语音侧处理，通过已经协商的设备音频格式和帧长下发。
- **控制请求**建议走内部 HTTPS JSON。一次动作携带场次 ID、回合 ID、请求 ID 和必要的音频引用。玩家身份由可信会话绑定。同一个请求重试返回原处理结果，旧回合的请求由场次拦截。
- **局面和播放指令**建议通过内部 SSE 事件流推送，即游戏侧在一个持续连接上向语音侧发送事件。事件带场次 ID 和顺序号，重连可按进度重取，或者读取该玩家的最新可见局面。媒体字节走语音通道。
- **跨节点音频**首轮真机验证先放在同一个语音节点。推广到不同节点时，语音侧按音频引用读取临时片段，当前场次和接收者决定可读范围。单个节点的临时缓冲在回合取消、结束或过期后清理。

### 原声什么时候进池

一轮在线交互使用短时音频缓冲。房间判定这句适合复用，且取得分享授权后，入池流程把完整原声保存到私有对象存储。**文件可读取后才把索引标记为可查。** 存储失败可以重试，已完成的在线回合仍可继续。相同的发布请求对应同一条记录。

游戏库保存音频引用、素材条件、授权和撤回状态。上线后的取用分两步，先按条件查候选，再在播放前按场次和收听者复核。撤回会关闭后续取用权限，已经听到的内容无法收回。留存音频建议统一为单声道 Opus，保留孩子原声里的节奏和语气。用于复用的片段长度、保留期限和分享范围需要一起定。

## 主要风险和验收

| 风险 | 预先设计 | 首轮怎么验证 |
| --- | --- | --- |
| 说完后的等待太长 | 把一句话结束、动作接收、B 听到首声和 B 获得发言权分开计时。回合转接尽量使用短提示。 | 用两台盒子测 A 说完到 B 听到首声、B 播完到能开口，记录 P50 和 P95。 |
| 盒子没播完就开麦 | 把「帧已发出」和「扬声器实际播完」分开处理。已知设备缓冲估算可用于首轮试测。 | 真机验证剪字、回声、自录本机扬声器和交棒过迟。 |
| 弱网或慢设备拖住全局 | 每个接收者有独立的有限播放队列。只等待对下一步确有影响的接收者，到期由房间处理。 | 给一台盒子制造网络延迟，观察其他玩家的播放、退出和后续回合。 |
| 抢答、退出或换房与播报冲突 | 播放和收音绑定当前场次、回合及接收者。私人控制可以先停本机，场次随后清理席位和发言权。 | A 发言时 B 抢答，再让 B 在播放中退出。检查 A 的局面和 B 回到 Buddy 的时间。 |
| 重连或重复请求推进两次 | 场次统一管理动作顺序，按请求 ID 去重。重连恢复当前局面，旧回合的迟到音频和指令过期。 | 重发动作、让盒子断线重连、在换房后延迟送到上一局的音频。 |
| 入池写入不完整，或者旧素材越权 | 索引在音频可读后发布。播放前复核对象状态、接收者和授权。 | 模拟写入失败、重复发布、候选选中后撤回，再尝试从另一局播放。 |
| 相似话题的录音接错上下文 | 房间给出明确的兼容条件，池子按条件筛选。编排顺序和素材含义由房间处理。 | 拿同一主题但来自不同故事位置的录音验证筛选。 |
| 好友离线被误认为在线 | 在线邀约和历史素材分别有来源。Buddy 在播放前用一句话标明这是好友以前留下的声音。 | 好友关机后开局，再让好友在播放历史素材时上线，检查本局的来源和进度。 |

## 首轮开发顺序

1. **在 GamingPlatform 定复用池接口和数据模型。** 先验发布、检索、授权取用、撤回。样本来源场次结束后，另一场次仍可用获准的原声。
2. **用两台真机验证语音能力。** 核对采一句、播原声、实际播完后的开麦，以及播放中触发私人控制。现有 MCP 可先跑文字动作和局面，用真机原声作为完整链路的验收点。
3. **接入故事接龙房间。** 先跑好友离线后的原声复用，再接好友邀请和同局轮流。之后用第二个简单规则模块走一遍同样的大厅入口和素材接口。

## 需要确认的边界

- 同一房型可以有独立的场次标识。产品是否允许同时开放多局、一个孩子是否能同时挂起多局，留到场次产品规则确认。
- 私人控制在盒子播放中的触发方式、录音结束的检测参数和可接受的交棒延迟，以目标机型实测决定。
- 录音分享对象、留存期限、撤回后的缓存清理和历史场次呈现，需要统一产品口径。
- 跨语音节点的媒体读取、场次规模和并发容量在首轮真机测量后定。HTTPS 加 SSE、单声道 Opus 是当前架构草案的接口与存储选择。
